# 缓存专项测试 Spec

## 背景

现有缓存测试依附于常规压测，通过预热请求后观察缓存 Token 指标，无法独立验证不同请求内容关系下缓存是否生效，也不能按 Case 明确区分命中、未命中、接口失败和上游未提供缓存证据。

需要新增一个与“新建测试”“自定义 Case”平级的缓存专项测试入口，集中验证常见的提示词缓存场景，并提供可追溯的逐 Case 结果。

## 目标

- 提供独立的“缓存专项测试”菜单入口和页面。
- 页面地址固定为 `/tests/cache-diagnostics`，路由名称固定为 `cache-diagnostics`。
- 自动验证重复请求、多轮对话和固定前缀尾部变化三种缓存场景。
- 使用上游返回的缓存用量作为判定证据，避免根据请求文本或延迟猜测缓存命中。
- 让用户能够查看每个 Case 的执行状态、缓存指标和失败原因。

## 功能需求

- F1: 已登录用户可以从侧边栏进入独立的“缓存专项测试”页面；该页面不嵌入现有“新建测试”或“自定义 Case”页面。
- F2: 页面允许配置接口协议、接入域名、Endpoint、API Key、模型、最大输出 Token、超时时间和是否开启流式响应。
- F3: 用户可以选择并执行以下缓存 Case，默认全部选中：
  - “缓存命中-重复请求”：先发送基准请求，再发送内容完全相同的验证请求。
  - “缓存命中-多轮对话”：先建立首轮上下文，再发送保留原上下文并新增一轮消息的验证请求。
  - “缓存命中-尾部变化”：两次请求保持足够长的公共前缀，仅改变尾部内容。
- F4: 每个 Case 必须按固定顺序执行准备请求和验证请求，单个 Case 的请求不得与该 Case 内的前置请求并发，以保证验证关系明确。
- F5: 每个 Case 展示 Case 名称、状态、判定结果、准备请求和验证请求的 HTTP 状态、总延迟、TTFT、输入/输出 Token、缓存命中 Token、缓存创建 Token、含缓存 Token、缓存命中率以及错误信息。
- F6: Case 判定必须区分四种结果：
  - “缓存命中”：验证请求返回明确且大于零的缓存命中 Token。
  - “未命中缓存”：上游明确返回缓存用量字段，但验证请求的缓存命中 Token 为零。
  - “无法判定”：请求成功，但上游没有返回可用于判断的缓存用量字段。
  - “执行失败”：准备请求或验证请求发生协议、网络、超时或 HTTP 错误。
- F7: 测试运行期间展示总体进度和当前 Case；完成后展示 Case 执行摘要，包括总数、缓存命中数、未命中数、无法判定数和执行失败数。
- F8: 测试结果应保存为独立任务，能够在历史记录中识别为“缓存专项测试”，并可重新打开结果页面查看，不与普通压测指标混合解释。
- F9: 缓存专项结果支持导出 PDF；PDF 至少包含测试配置、执行摘要、逐 Case 判定、两阶段请求的缓存与延迟指标以及错误信息。

## 非功能需求

- N1: API Key 不得写入结果、历史记录、日志或 PDF。
- N2: 单次专项测试最多执行三个内置 Case，不提供并发压测和矩阵压测，避免缓存诊断被负载竞争干扰。
- N3: OpenAI、Anthropic 和 Gemini 协议均可发起测试；若目标服务不提供缓存用量字段，必须显示“无法判定”。
- N4: TTFT 仅在流式响应且采集到首 Token 时展示；缺失时显示“不可用”，真实零值仍按零值展示。
- N5: 现有普通压测、自定义 Case、历史任务和报告行为保持兼容。

## 不做的事

- 不根据响应耗时降低、回答内容相似或请求文本重复推断缓存命中。
- 不验证服务端缓存过期时间、跨账号缓存共享、跨模型缓存共享或缓存淘汰策略。
- 不允许用户自定义 Case 脚本、任意请求链或缓存判定表达式。
- 不把缓存专项测试用于 RPM、QPS、TPM 或并发容量评估。
- 不修改上游服务的缓存策略，也不保证所有兼容接口都会返回缓存用量字段。

## 验收标准

- AC1: 已登录用户在侧边栏看到“缓存专项测试”，点击后进入 `/tests/cache-diagnostics`，刷新页面仍能正常访问，且路由名称为 `cache-diagnostics`。
- AC2: 页面默认勾选三个内置缓存 Case，用户填写连接配置后可以一次启动全部选中 Case。
- AC3: 三个 Case 分别按“重复请求”“保留多轮上下文”“公共前缀不变且尾部变化”的关系生成并顺序发送准备请求与验证请求。
- AC4: 验证请求返回大于零的缓存命中 Token 时显示“缓存命中”，并展示对应缓存 Token 和命中率。
- AC5: 上游明确返回缓存字段但命中 Token 为零时显示“未命中缓存”；完全没有缓存字段时显示“无法判定”，两者不得混淆。
- AC6: 任一阶段请求失败时，该 Case 显示“执行失败”，并展示失败阶段、HTTP 状态或错误类型和错误信息，其余 Case 可以继续执行。
- AC7: 完成后摘要数量与逐 Case 结果一致，并能查看每个 Case 两阶段请求的延迟、TTFT、Token 和缓存指标。
- AC8: 从历史记录能够识别并重新打开缓存专项任务，结果含义不会按普通负载测试展示。
- AC9: 导出的 PDF 包含配置、摘要、三个 Case 的判定与请求证据；API Key 不出现在页面持久化结果或 PDF 中。
- AC10: 非流式模式或未采集到首 Token 时 TTFT 显示“不可用”；实际 TTFT 为零时仍显示零值。
- AC11: 现有普通单次压测、矩阵压测和自定义 Case 的创建及报告仍可正常使用。
