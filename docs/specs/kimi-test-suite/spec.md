# Kimi 能力测试集 Spec

## 背景

当前系统支持普通压测、批量自定义 Case 和缓存专项测试，但没有面向 Kimi OpenAI 兼容接口的独立能力验收流程。截图所示测试结果需要同时验证请求参数是否生效、响应格式是否符合约定、工具调用是否可用、Token 限制是否生效，以及缓存 usage 是否真实返回。

## 目标

- 提供独立的 Kimi 能力测试集入口，默认使用 OpenAI 兼容接口和 `kimi-k3` 模型。
- 将每项能力作为独立 Case 执行、判定并展示，便于定位单项兼容性问题。
- 对缓存能力采用真实 usage 字段判定，不根据延迟、文本相似度或请求顺序推断命中。
- 保持现有普通压测、矩阵压测、缓存专项和自定义 Case 流程兼容。

## 功能需求

- F1: 用户可以配置 Kimi 测试集的 Base URL、Endpoint、API Key、模型、流式模式、超时和重试参数；默认 Endpoint 为 `/v1/chat/completions`，默认模型为 `kimi-k3`。
- F2: 系统提供以下 9 个内置 Case，并默认全部选中：重复请求缓存、多轮对话缓存、尾部变化缓存、思考控制、JSON 格式输出、stop 参数、采样参数、工具调用和输出 Token 校验。截图中的“多场景”能力可以由一个聚合 Case 展示。
- F3: 每个非缓存 Case 可以使用独立的请求参数，包括 thinking、`response_format`、`stop`、`temperature`、`top_p`、`tools`、`tool_choice` 和 `max_tokens`。
- F4: 系统按 Case 顺序执行测试，并为每个 Case 记录请求参数摘要、HTTP 状态、耗时、首 token、重试次数、usage 数据、响应断言证据和脱敏响应片段。
- F5: JSON Case 必须验证响应内容可解析为 JSON；stop Case 必须验证停止序列后未出现禁止内容；工具 Case 必须验证工具名称、调用类型和参数；输出 Token Case 必须验证输出 Token 不超过限制。
- F6: 思考控制 Case 必须分别验证思考开启和关闭场景；当上游缺少可验证字段或明确不支持参数时，结果必须标记为无法判定或接口不支持，不得误判为通过。
- F7: 缓存 Case 必须分别覆盖重复请求、多轮对话和尾部变化；缓存结果只能依据上游返回的缓存 usage 字段分类为缓存命中、未命中、无法判定或执行失败。
- F8: 系统提供与设计截图一致的结果表，至少展示 Case 名称、Endpoint、脱敏 API Key、供应商模型、状态、耗时、首 token、重试、人工重跑和失败原因。
- F9: 用户可以查看测试集的总体结果和逐 Case 详情；单个 Case 失败时，其他 Case 仍继续执行并保留结果。
- F10: 测试结果可保存到历史记录和结果文件，且页面、日志、历史记录、JSON/JSONL 和报告中均不得出现 API Key 或认证头。

## 非功能需求

- N1: 首版只支持 OpenAI 兼容协议，不实现 Moonshot 原生协议。
- N2: 缓存 Case 使用串行请求，不纳入并发容量压测；普通 Case 的请求规模保持有限，避免测试集本身产生高额调用成本。
- N3: 测试判定必须区分“接口不支持”“响应不可判定”“请求执行失败”和“断言失败”。
- N4: 新增测试集不得改变现有普通压测、矩阵压测、缓存专项、自定义 Case、历史记录和报告导出行为。

## 不做的事

- 不实现 Moonshot 原生 API 适配。
- 不根据响应延迟、文本相似度或模型自述推断缓存命中或 thinking 状态。
- 不将 Kimi 能力测试集扩展为通用任意脚本执行器。
- 不在首版实现跨模型横向排名、自动重试策略改造或计费分析。

## 验收标准

- AC1: 用户打开独立 Kimi 测试集入口时，连接配置默认显示 OpenAI 兼容协议、`/v1/chat/completions` 和 `kimi-k3`，提交后生成一个独立测试任务。
- AC2: 用户可以选择内置 Case；默认选择全部 Case，提交空列表、未知 Case 或重复 Case 时得到明确校验错误。
- AC3: 每个非缓存 Case 的最终请求体只包含自身配置的参数；JSON、stop、采样、工具和 `max_tokens` 场景均可在请求明细中复核。
- AC4: 合法 JSON 响应通过，非法 JSON 响应失败；stop 序列后的禁止内容、错误工具名称或错误工具参数、超出输出 Token 限制均判定失败。
- AC5: thinking 开启、关闭和不支持/缺失字段场景分别得到通过、失败或无法判定/接口不支持，不将缺失证据判定为通过。
- AC6: 三个缓存 Case 生成正确的请求序列，并且只有返回缓存 usage 字段时才能判定缓存命中或未命中；字段缺失时显示无法判定。
- AC7: 任一 Case 失败不会阻断其他 Case；结果表能展示全部 Case 的状态、耗时、首 token、重试次数和失败原因。
- AC8: 测试完成后可重新打开历史结果和逐 Case 详情，结果文件包含断言证据与 usage 数据且不包含 API Key、认证头或未脱敏敏感信息。
- AC9: 现有普通压测、矩阵压测、缓存专项和自定义 Case 的既有测试继续通过，且其创建、执行、历史查看和报告流程不发生回归。
