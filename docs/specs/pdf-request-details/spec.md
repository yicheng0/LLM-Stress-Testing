# PDF 请求明细完整化 Spec

## 背景

当前网页请求明细会展示请求结果、状态码、延迟、TTFT、Token、缓存和错误信息，但下载的 PDF 只展示了其中一部分，导致离线报告无法完整追溯每条请求。

## 目标

- PDF 导出报告完整呈现每条请求的执行结果、性能、Token、缓存和错误信息。
- 在 A4 页面中保持字段可读，不出现横向截断、重叠或无法对应到请求 ID 的情况。
- 保持现有汇总指标、延迟分布、图表和矩阵报告能力不变。

## 功能需求

- F1: 单次测试 PDF 必须包含请求明细，覆盖 ID、结果、状态码、延迟、TTFT、输入 Token、输出 Token、总 Token、缓存命中 Token、缓存创建 Token、含缓存 Token、缓存命中率、TPS、错误类型和错误信息。
- F2: 成功和失败请求都必须进入请求明细；没有错误的请求在错误字段中显示空值或“-”，失败请求保留实际状态码、错误类型和错误信息。
- F3: TTFT、TPS 或其他未采集字段必须显示“不可用”，真实数值 0 不能被当作缺失。
- F4: 明细字段可以按性能与 Token、状态与错误分组展示，但每组必须保留请求 ID，确保同一请求可以准确对应。
- F5: 历史任务下载 PDF 时使用现存详情数据重新生成新版报告；历史数据中不存在的字段不推算或伪造。

## 非功能需求

- N1: PDF 使用 A4 页面导出，请求明细允许跨页，表头在分页后保持可识别。
- N2: 表格不得出现字段被裁切、文字重叠或错误信息撑破页面的问题。
- N3: 不修改压测采集算法、数据库结构和现有下载接口。

## 不做的事

- 不在 PDF 中加入请求或响应正文、API Key 等敏感数据。
- 不修改网页请求明细的字段和交互。
- 不为历史任务缺失的数据建立估算值。
- 不改变矩阵测试的逐请求数据模型。

## 验收标准

- AC1: 导出包含成功与失败请求的单次测试 PDF，能够看到 F1 中列出的全部字段。
- AC2: 成功请求显示 OK、实际状态码、Token 与缓存数据；错误字段为空值或“-”。
- AC3: 失败请求显示 FAIL、实际状态码、错误类型和错误信息，并能通过 ID 定位请求。
- AC4: TTFT 缺失时显示“不可用”，TTFT 为 0 时显示为真实零值。
- AC5: 多页请求明细的表头清晰，页面无横向截断、重叠和不可读列。
- AC6: 已存在旧 PDF 的历史任务再次下载时重新生成，并在详情数据允许的范围内展示新版字段。
