# PDF 请求明细完整化 Plan

## 架构概览

保持现有 PDF 下载链路不变：下载接口读取任务摘要和详情 JSONL，PDF 服务将详情转换为可打印 HTML，再由 Playwright 生成 PDF。改动集中在 PDF 服务的数据格式化和明细布局，不修改数据库、压测采集、网页报告或下载接口。

请求明细采用两张按 ID 对齐的表格：第一张展示状态、延迟和 Token，第二张展示缓存与错误。这样可以完整容纳字段，同时避免 A4 页面出现超宽表截断。

## 核心数据结构

### PDF 请求明细行

从每条已有请求详情读取并格式化以下字段：

- `request_id`：两张表共同的关联键。
- `result`：根据请求是否成功显示 `OK` 或 `FAIL`。
- `status`：实际 HTTP 状态码。
- `latency`、`ttft`：秒级延迟；缺失为“不可用”，真实零值保留。
- `input_tokens`、`output_tokens`、`total_tokens`：请求 Token 数据。
- `cached_input_tokens`、`cache_creation_input_tokens`、`cache_inclusive_total_tokens`：缓存 Token 数据。
- `cache_hit_rate`：沿用现有 PDF 单请求缓存命中率口径。
- `tps`：沿用现有 PDF 单请求 TPS 口径；无法计算时显示“不可用”。
- `error_type`、`error_message`：成功请求显示“-”，失败请求显示原始安全错误信息。

## 核心接口

### PDF HTML 渲染入口

现有入口继续接收摘要、图表和请求详情；单次报告渲染时把完整详情交给请求明细组件。调用方式和下载 API 不变。

### 请求明细渲染

请求明细渲染输出两个连续章节：

1. “请求状态、延迟与 Token”：ID、结果、状态码、总延迟、TTFT、输入 Token、输出 Token、总 Token、TPS。
2. “请求缓存与错误”：ID、缓存命中 Token、缓存创建 Token、含缓存 Token、缓存命中率、错误类型、错误信息。

两张表均按同一详情顺序输出成功和失败请求，不再只在第一张表列成功样本。现有失败摘要保留，用于快速查看失败类型聚合。

## 模块设计

### PDF 数据格式化

**职责：** 从字典或请求结果对象安全读取字段，计算现有派生指标，统一格式化缺失值和真实零值。

**对外接口：** 供单次 PDF 明细渲染使用的内部格式化结果。

**依赖：** 现有请求详情字段和数值格式化函数。

### PDF 明细布局

**职责：** 输出两张窄表，并控制列宽、错误文本换行、跨页表头和单行分页行为。

**对外接口：** 单次报告正文中的“单次请求明细”章节。

**依赖：** PDF 数据格式化结果。

### PDF 下载重渲染

**职责：** 继续在每次下载时读取详情 JSONL、生成临时 PDF 并原子替换旧文件。

**对外接口：** 现有 PDF 下载响应。

**依赖：** 现有下载接口与 PDF 生成流程，无接口变化。

## 模块交互

```text
PDF 下载请求
  -> 读取 Summary 与详情 JSONL
  -> 回填可恢复的 TTFT/Decode 汇总
  -> 生成图表数据
  -> 格式化逐请求明细
  -> 渲染两张请求明细表
  -> Playwright 生成临时 PDF
  -> 原子替换历史 PDF
  -> 返回下载文件
```

## 技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 明细布局 | 两张按 ID 对齐的表 | 15 个字段放在单张 A4 表中不可读且容易截断 |
| 请求范围 | 成功和失败请求全部展示 | 满足逐请求追溯，避免失败请求只存在聚合摘要 |
| 错误展示 | 错误类型与错误信息放在缓存/错误表 | 为长文本提供更宽列，降低页面撑破风险 |
| 缺失值 | 使用“不可用”；错误空值使用“-” | 区分未采集指标与正常无错误状态 |
| 历史报告 | 每次下载读取现有详情并重新渲染 | 无需迁移数据库，同时让历史任务获得新版模板 |
| 接口兼容 | 不增加 API 或持久化字段 | 所需数据已经存在于详情 JSONL |
