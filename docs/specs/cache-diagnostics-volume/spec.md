# 缓存专项可配置样本量 Spec

## 背景

当前缓存专项测试为每个 Case 固定发送一次准备请求和一次验证请求，并固定使用约 4096 Token 的公共前缀。两次请求只能判断单个验证样本是否命中，无法观察连续多次请求中的实际命中比例；固定 Token 长度也不能覆盖不同模型和供应商的缓存门槛。

需要允许用户自定义公共前缀 Token 长度和每个 Case 的请求次数，通过多个连续验证样本统计缓存命中率，并在页面、历史结果和 PDF 中完整展示。

## 目标

- 缓存专项配置页支持自定义公共前缀 Token 长度。
- 缓存专项配置页支持自定义每个 Case 的请求次数。
- 每个 Case 使用第一次请求建立缓存，后续请求作为验证样本。
- 根据全部可判定验证样本统计 Case 命中率和任务总体命中率。
- 页面和 PDF 同时展示配置值、执行进度、汇总命中率和逐请求证据。

## 功能需求

- F1: 用户可以配置公共前缀 Token 长度，默认值为 4096 Token，必须为正整数。
- F2: 用户可以配置每个 Case 的请求次数，默认值为 10 次，最少为 2 次，最多为 100 次。
- F3: 请求次数按每个选中的 Case 独立计算。例如选择 3 个 Case、请求次数为 10 时，任务计划发送 30 次请求，不包含失败重试产生的额外尝试。
- F4: 每个 Case 的第 1 次请求为缓存建立请求，不计入缓存命中率；第 2 次至最后一次请求为验证请求。
- F5: 同一 Case 的所有请求必须严格串行执行。停止任务后不得启动新的验证请求或后续 Case。
- F6: 重复请求 Case 的验证请求与缓存建立请求保持相同内容关系；尾部变化 Case 的所有验证请求保持公共前缀不变并使用验证尾部；多轮对话 Case 的后续请求保留此前真实对话上下文并继续追加新一轮消息。
- F7: 每个验证请求按照上游缓存字段分别判定为“缓存命中”“未命中缓存”“无法判定”或“执行失败”。
- F8: 每个 Case 展示计划请求数、已执行请求数、验证样本数、缓存命中数、未命中数、无法判定数、失败数和 Case 命中率。
- F9: Case 命中率以可判定验证样本为分母，计算方式为“缓存命中验证数 /（缓存命中验证数 + 未命中验证数）”。缓存建立请求、无法判定请求和失败请求不进入分母；分母为零时显示“不可用”。
- F10: 任务总体命中率使用所有 Case 的可判定验证样本合并计算，不对各 Case 命中率做简单平均。
- F11: 运行进度展示当前 Case、当前请求序号、已执行请求数和计划总请求数。
- F12: 结果页面和 PDF 展示公共前缀目标 Token、实际公共前缀 Token、每个 Case 请求次数、计划总请求数、实际请求数、总体命中率、各 Case 命中率及全部逐请求指标。
- F13: 历史任务仍可重新打开；旧版缓存专项任务缺少新配置时，按原来的两次请求结构展示，不伪造新增验证样本或命中率。

## 非功能需求

- N1: API Key、完整公共前缀、完整请求正文和完整模型回复不得写入 Summary、Details、事件、HTML、Markdown 或 PDF。
- N2: 缓存专项仍保持并发数为 1，不用于 RPM、QPS、TPM 或并发容量评估。
- N3: 公共前缀应尽量达到用户设置的 Token 长度，并同时记录目标值和实际估算值；页面和报告不得把目标值冒充为上游实际输入 Token。
- N4: OpenAI、Anthropic 和 Gemini 均沿用现有缓存字段判定口径。上游没有返回缓存字段时显示“无法判定”。
- N5: TTFT 仅在流式响应采集到首个模型 Token 时显示；缺失时显示“不可用”，真实零值仍显示为零。
- N6: 增加请求次数后仍必须支持停止、失败隔离、历史记录、结果保留和 PDF 原子替换。
- N7: 普通单次压测、矩阵压测和自定义 Case 的行为保持不变。

## 不做的事

- 不开放并发缓存请求、缓存持续时间或请求间隔配置。
- 不根据耗时降低、文本相似度或请求顺序推断缓存命中。
- 不将缓存建立请求计入命中率。
- 不把“无法判定”或“执行失败”当作未命中缓存。
- 不新增用户自定义请求链或缓存判定表达式。
- 不修改数据库结构。

## 验收标准

- AC1: 配置页显示“公共前缀 Token”和“每个 Case 请求次数”，默认分别为 4096 和 10；请求次数小于 2、大于 100或 Token 非正整数时不能启动任务。
- AC2: 选择 3 个 Case 且请求次数为 10 时，页面显示计划请求总数为 30，并按 Case 严格串行发送 30 个业务请求；失败重试不增加计划请求总数。
- AC3: 每个 Case 的第 1 次请求标记为“缓存建立”，其余请求标记为“缓存验证”，缓存建立请求不进入命中率。
- AC4: 某 Case 的 9 个验证请求中有 6 个命中、2 个未命中、1 个无法判定时，Case 命中率显示为 75.00%，而不是 66.67%。
- AC5: 所有验证请求均无法判定或失败时，Case 命中率和总体命中率显示“不可用”。
- AC6: 多个 Case 的总体命中率按全部可判定验证请求合并计算，结果与逐请求明细一致。
- AC7: 运行页实时展示当前 Case、当前请求序号和“已执行 / 计划总请求数”，任务停止后不再发送新的业务请求。
- AC8: 结果页为每个 Case 展示完整统计，并能查看每一次缓存建立或验证请求的状态码、延迟、TTFT、Token、缓存字段、单请求判定和错误信息。
- AC9: PDF 展示 Token 长度、请求次数、总体与逐 Case 命中率以及全部逐请求证据，长表自动分页且不截断。
- AC10: Summary、Details、HTML、Markdown、事件和 PDF 中不出现 API Key、完整公共前缀、完整请求正文或完整模型回复。
- AC11: 打开旧版缓存专项历史任务时仍能正常显示原有准备/验证结果，缺失的新统计字段显示“不可用”或按旧数据可直接计算的值展示，不伪造请求。
- AC12: 普通单次压测、矩阵压测、自定义 Case 和原有 PDF 下载行为保持正常。
